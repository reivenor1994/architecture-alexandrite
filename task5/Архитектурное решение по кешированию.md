# Задание 5. Кеширование

## 1. Анализ

Компоненты, которые подходят для кеширования:

**MES API**:

  - Списки заказов с фильтрами
  - Данные по отдельным заказам
  - Результаты расчетов стоимости
  - Справочники

**Shop API**:

  - Данные о товарах и категориях
  - Статусы заказов

**CRM API**:

  - Справочники

## 2. Мотивация

**Проблемы текущей системы**:
  - Медленная загрузка страницы списка заказов в MES API
  - Долгий расчет стоимости
  - Задержки при обновлении статусов заказов
  - Высокая нагрузка на БД MES API из-за частых запросов списка заказов

**Цели внедрения кеширования**:

  - Повысить стабильность системы
  - Снизить нагрузку на БД
  - Улучшить отзывчивость UI
  - Оптимизировать расчет стоимости

Элементы системы для кеширования описаны в пункте 1. Анализ

## 3. Предлагаемое решение

**Тип кеширования**: Серверное кеширование

Обоснование:

  - Данные должны быть едиными для всех операторов
  - Требуется централизованное управление инвалидацией
  - Большой объем данных (неэффективно хранить на клиенте)

**Паттерн кеширования**: Cache-Aside

Преимущества:

  - Простота реализации
  - Эффективен для read-heavy workload
  - Не требует сложной синхронизации

Альтернативы:
  - Write-Through: избыточен, так как не все данные требуют мгновенного обновления
  - Refresh-Ahead: сложно предсказать, какие данные понадобятся

**Стратегия инвалидации кеша**:

Для системы оптимальной будет комбинация нескольких стратегий, так как разные данные требуют разного подхода к актуальности

| Тип данных                | Стратегия инвалидации                 | Почему?                                                                  | Пример                                                                        |
|---------------------------|---------------------------------------|--------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| Списки заказов            | Временная (TTL) + На основе изменений | Данные меняются не мгновенно, но требуют обновления при изменениях.      | TTL = 5 мин + инвалидация при изменении статуса любого заказа в списке        |
| Данные конкретного заказа | По ключу + На основе изменений        | Необходима мгновенная актуальность при изменении статуса.                | Ключ `order:{id}` инвалидируется при `PUT /orders/{id}/status`                |
| Расчеты стоимости         | Временная (TTL) + По ключу            | Результаты расчетов статичны, но могут измениться при обновлении модели. | TTL = 24 часа + инвалидация при изменении 3D-модели (ключ `calculation:{id}`) |
| Справочники               | Временная (TTL)                       | Данные меняются редко (раз в день).                                      | TTL = 12 часов                                                                |

Почему другие стратегии не подходят:

| Стратегия           | Подходит для                    | Плюсы                          | Минусы                                   | Почему не подходит?                 |
|---------------------|---------------------------------|--------------------------------|------------------------------------------|-------------------------------------|
| Временная           | Данные с допустимой задержкой   | Простота, низкая нагрузка      | Риск устаревания данных                  | Не подходит для статусов заказов    |
| По ключу            | Точечные изменения              | Точность, минимальный overhead | Сложность отслеживания                   | Не защищает от "зависания" данных   |
| На основе изменений | Критичные к актуальности данные | Мгновенное обновление          | Высокая нагрузка при массовых изменениях | Избыточно для справочников          |
| На основе запросов  | Явные сценарии обновления       | Полный контроль                | Требует изменения клиентского кода       | Неудобно для фоновых процессов      |
| Программная         | Сложные бизнес-правила          | Максимальная гибкость          | Сложность реализации                     | Избыточна для большинства сценариев |
