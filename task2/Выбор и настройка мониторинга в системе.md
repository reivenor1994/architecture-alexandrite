# Задание 2. Мониторинг

## 1. Мотивация

Возможности, которые предоставляет мониторинг:

- **В режиме реального времени видеть состояние системы** - оперативный контроль за ключевыми показателями.
- **Получать алерты при приближении к критическим значениям** - своевременное оповещение о потенциальных проблемах.
- **Анализировать исторические данные для поиска закономерностей** - выявление тенденций и прогнозирование будущих
  проблем.
- **Обосновывать необходимость изменений архитектуры** - принятие обоснованных решений об улучшениях и оптимизации
  системы.

Внедрение мониторинга даст компании:

- **Снижения количества жалоб клиентов** - позволит выявлять проблемы до того, как о них узнают пользователи.
- **Оперативного реагирования на сбои** - уменьшит время простоя системы.
- **Анализа узких мест** - поможет понять, где именно система не справляется с нагрузкой.
- **Планирования масштабирования** - предоставит данные для обоснования увеличения ресурсов.
- **Снижения потерь бизнеса** - предотвратит потерю заказов и клиентов.

## 2. Выбор подхода к мониторингу

Для комплексного мониторинга системы необходим гибридный подход, используя разные методологии для различных компонентов:

1. **Для пользовательских API (Shop API, CRM API, MES API) - "Четыре золотых сигнала"**

**Обоснование:** API являются точками взаимодействия с клиентами, поэтому важно отслеживать именно пользовательский
опыт.

**Преимущества:**

- Позволяет быстро выявлять проблемы, влияющие на клиентов
- Дает полную картину качества сервиса

2. **Для RabbitMQ - USE**

**Обоснование:** Очереди сообщений - это инфраструктурный компонент, где важны ресурсы и надежность.

**Преимущества:**

- Позволяет предотвращать проблемы до их возникновения
- Оптимален для систем очередей
- Помогает правильно масштабировать

3. **Для баз данных - USE**

**Обоснование:** Базы данных - критичный ресурсоемкий компонент.

**Преимущества:**

- Помогает выявлять проблемы с производительностью БД
- Обеспечивает эффективное использование ресурсов
- Позволяет оптимизировать запросы

4. **Для бизнес-процессов - RED**

**Обоснование:** Для сквозного мониторинга ключевых бизнес-метрик.

**Преимущества:**

- Обеспечивает прозрачность бизнес-процессов
- Позволяет выявлять узкие места и задержки
- Дает возможность оперативно реагировать на проблемы в бизнес-логике

## 3. Метрики для отслеживания

### 1. RabbitMQ

| Метрика                                | Зачем                                              | Ярлыки                       | Почему такие ярлыки                                                                                                           |
|----------------------------------------|----------------------------------------------------|------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| Number of dead-letter-exchange letters | Выявить потерянные сообщения (риск потери заказов) | `queue_name`, `error_type`   | `queue_name` - идентификация проблемной очереди; <br/>`error_type` - классификация ошибок (например, "timeout", "validation") |
| Number of message in flight            | Контроль задержек обработки                        | `queue_name`, `consumer_tag` | `consumer_tag` - поможет найти "медленного" потребителя очереди                                                               |

### 2. API сервисы (Shop/CRM/MES)

| Метрика                        | Зачем                                                  | Ярлыки                             | Почему такие ярлыки                                                                                                                                                                                                       |
|--------------------------------|--------------------------------------------------------|------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Number of requests (RPS)       | Оценить нагрузку                                       | `endpoint`, `method`, `user_type`  | `endpoint` - точно идентифицирует, какой URL API вызывает проблемы; <br/> `method` - разделяет нагрузку по типам операций; <br/> `user_type` (например, "operator", "seller") - выявить аномалии в действиях разных ролей |
| Response time (latency)        | Ухудшение UX при росте времени ответа                  | `endpoint`, `method`, `status`     | `status` (HTTP-код) - отделить медленные успешные запросы от ошибок                                                                                                                                                       |
| Number of HTTP 500             | Критические сбои                                       | `endpoint`, `method`, `error_code` | `error_code` (например, "db_timeout") - для быстрой диагностики                                                                                                                                                           |
| Kb tranferred  (sent/received) | Выявить аномальный трафик (например, большие 3D-файлы) | `endpoint`, `direction` (in/out)   | `direction` - разделить входящий/исходящий трафик                                                                                                                                                                         |

### 3. Базы данных

| Метрика               | Зачем                        | Ярлыки                               | Почему такие ярлыки                                                                                                        |
|-----------------------|------------------------------|--------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| Memory Utilisation    | Предотвратить OOM-сбои       | `database_name`, `type` (heap/cache) | `database_name` - бд для которой произошло событие; <br/> `type` - разделить использование памяти под кеш и рабочие данные |
| Number of connections | Обнаружить утечки соединений | `database_name`, `user`              | `user` - дентификация проблемного клиента БД                                                                               |
| Size of db instance   | Планировать масштабирование  | `database_name`, `table`             | `table` - выявить "раздутые" таблицы                                                                                       |

|---------------------------|-------------------------------|--------------------------------|---------------------------------------------------------------------------------------------|

| 3d_model_calculation_time | Выявить проблемные модели     | `complexity` (low/medium/high) | `complexity` - связать время расчета с 3д моделью                                           |

## 4. План действий

**Настройка Grafana:**

  - Импортировать или создать базовые дашборды.

**Развертывание ELK:**
  - Развернуть Elasticsearch, Logstash и Kibana для сбора, обработки и анализа логов.
  - Настроить Logstash для получения логов из различных источников.

**Настройка Alertmanager:**
  - Установить и настроить Alertmanager для управления и отправки алертов.
  - Определить каналы уведомлений.

### 2. Инструментирование приложений:

**Добавление Prometheus клиентов в Java/C# приложения:**
  - Интегрировать Prometheus client libraries в Java и C# приложения для экспорта кастомных метрик.
  - Определить ключевые метрики для каждого приложения.

**Настройка экспортера для RabbitMQ:**
  - Установить и настроить RabbitMQ экспортера для сбора метрик о состоянии очередей и производительности RabbitMQ.

**Настройка экспортера для PostgreSQL:**
  - Установить и настроить PostgreSQL экспортера для сбора метрик о производительности базы данных и использовании ресурсов.

### 3. Создание дашбордов:

**Общий дашборд состояния системы:**
  - Создать дашборд, отображающий общее состояние системы, включая загрузку CPU, использование памяти, сетевой трафик и количество ошибок.

**Дашборды для каждого API:**
  - Создать отдельные дашборды для каждого API, отображающие количество запросов, время ответа, количество ошибок и другие ключевые метрики.

**Дашборд очередей RabbitMQ:**
  - Создать дашборд, отображающий состояние очередей RabbitMQ, включая количество сообщений, скорость обработки и задержки.

**Дашборд баз данных:**
  - Создать дашборд, отображающий состояние баз данных, включая использование ресурсов, количество запросов, время выполнения запросов и количество ошибок.

**Бизнес-дашборд (статусы заказов):**
  - Создать дашборд, отображающий ключевые бизнес-показатели: количество заказов, статусы заказов и среднее время обработки заказов.

### 4. Настройка алертов:

**Критические ошибки:**
  - Настроить алерт на срабатывание при превышении заданного порога ошибок HTTP 500.

**Рост очередей RabbitMQ:**
  - Настроить алерт на срабатывание при увеличении размера очередей RabbitMQ сверх допустимого уровня.

**Долгие расчеты стоимости (> 10 минут):**
  - Настроить алерт на срабатывание, если расчет стоимости занимает более 10 минут.

**Зависшие заказы (> 7 дней без изменения статуса):**
  - Настроить алерт на срабатывание при наличии заказов, которые не изменяли свой статус более 7 дней.

**Нехватка ресурсов (CPU > 80%, память > 90%):**
  - Настроить алерты на срабатывание при превышении пороговых значений использования CPU и памяти.
